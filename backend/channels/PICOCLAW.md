# PicoClaw ↔ GamCiv messaging integration

[PicoClaw](https://github.com/sipeed/picoclaw) is the messaging hub for
GamCiv's chat channels: it runs the Telegram bot natively (its own Telegram
channel) and WhatsApp through a small bridge, and it talks to GamCiv via the
`agent-api` edge function (this folder's sibling: `../functions/agent-api/`).

What PicoClaw provides out of the box (no custom code): channel adapters
(Telegram, WhatsApp bridge protocol, Discord, …), the message bus, send
retries with backoff, media handling, model plugging (any OpenAI-compatible
endpoint), sessions/memory, and MCP tool support.

What we had to write (the glue PicoClaw cannot do):

| Piece | Location | Purpose |
|---|---|---|
| `agent-api` | `../functions/agent-api/` | Edge function exposing GamCiv to PicoClaw as MCP tools (`gamciv_report`, `gamciv_status`) plus REST endpoints. Files reports via the same `submit_complaint` RPC the intake functions use, queues the SMS confirmation through the existing `notifications` → `notify-out` path, and optionally sends an email confirmation (Resend). |
| `gowa-bridge` | `gowa-bridge/` (this folder) | Converts GOWA webhooks into PicoClaw's WhatsApp bridge protocol (WebSocket frames) so the PicoClaw agent can read and reply to WhatsApp chats. |

## Architecture

```
                   Telegram (native channel)          WhatsApp
                            │                             │
                            ▼                             ▼
                      ┌─────────────┐   ws://…:3001   ┌─────────────┐
                      │   PicoClaw  │◄────────────────│ gowa-bridge │
                      │   gateway   │                 │  (Deno)     │
                      └──────┬──────┘                 └──────┬──────┘
                             │ MCP (HTTP, Bearer key)        │ webhook
                             ▼                               ▼
                      ┌─────────────┐                 ┌─────────────┐
                      │  agent-api  │                 │    GOWA     │
                      │ (edge func) │                 │  (WhatsApp) │
                      └──────┬──────┘                 └─────────────┘
                             │ RPC
                             ▼
                      ┌─────────────┐
                      │  Postgres   │  (routing, SLA, notifications)
                      └─────────────┘
```

- **Telegram**: PicoClaw's own channel polls the Bot API; the bot token lives
  in PicoClaw's `config.json` (`channel_list.telegram`).
- **WhatsApp**: GOWA keeps its existing webhook to `whatsapp-intake`
  (citizen intake stays exactly as it is). The bridge ADDS a second consumer:
  GOWA sends the same events to `gowa-bridge` (per-device webhook URL), which
  converts them to PicoClaw's bridge frames. The PicoClaw agent answers
  WhatsApp chats through the bridge (`{type:"message", to, content}` → GOWA
  `POST /send/message`).
- **GamCiv actions**: the agent calls `mcp_gamciv_report` / `mcp_gamciv_status`
  tools (MCP over HTTP with `Authorization: Bearer $AGENT_API_KEY`).

## GOWA bridge protocol (verified against PicoClaw source)

PicoClaw's WhatsApp channel is a **WebSocket client** that dials
`channel_list.whatsapp.settings.bridge_url` (default `ws://localhost:3001`):

- inbound frame → PicoClaw:
  `{type:"message", from, chat, content, media:[], id, from_name}`
- outbound frame → bridge:
  `{type:"message", to:"<chat jid>", content:"<text>"}` — text only
- no ping/pong, no reconnect: if the bridge restarts, PicoClaw must reload
  (`POST http://127.0.0.1:18790/reload`) or the container restarted; hence the
  bridge runs as a systemd service with `Restart=always` and starts before
  PicoClaw.
- `allow_from` is required: missing/empty accepts everyone.

## PicoClaw config (generated by scripts/deploy-messaging.sh)

```json
{
  "version": 3,
  "agents": {
    "defaults": {
      "model_name": "gamciv",
      "workspace": "/opt/picoclaw/data/workspace",
      "restrict_to_workspace": true,
      "max_tool_iterations": 20
    }
  },
  "model_list": [
    {
      "model_name": "gamciv",
      "provider": "openai",
      "model": "@cf/zai-org/glm-5.3-flash",
      "api_base": "https://api.cloudflare.com/client/v4/<account>/ai/v1",
      "api_keys": ["<OPENAI_API_KEY>"],
      "enabled": true
    }
  ],
  "channel_list": {
    "telegram": {
      "enabled": true,
      "type": "telegram",
      "allow_from": ["<TELEGRAM_USER_ID>"],
      "settings": { "token": "<PICTCLAW_TELEGRAM_BOT_TOKEN>" }
    },
    "whatsapp": {
      "enabled": true,
      "type": "whatsapp",
      "allow_from": ["<WHATSAPP_SENDER>"],
      "settings": { "bridge_url": "ws://172.17.0.1:3001" }
    }
  },
  "tools": {
    "exec": { "enabled": false },
    "web": { "enabled": false },
    "cron": { "enabled": false },
    "mcp": {
      "enabled": true,
      "servers": {
        "gamciv": {
          "enabled": true,
          "type": "http",
          "url": "https://api.pocketsoftware.dev/functions/v1/agent-api/mcp",
          "headers": { "Authorization": "Bearer <AGENT_API_KEY>" }
        }
      }
    }
  }
}
```

Hard restriction (config-only, three layers):

1. `tools.*.enabled: false` for everything except `mcp` (exec, web, cron,
   write tools, spawn, subagent…).
2. `channel_list.*.allow_from` with explicit sender allowlists.
3. `workspace/AGENT.md` limiting the agent to the two GamCiv tools.

## Local development

```bash
cd backend
deno test --allow-all        # includes gowa-bridge + agent-api tests
deno lint
```

Run the bridge locally (it only listens on 127.0.0.1):

```bash
set -a; source .env; set +a
deno run --allow-net --allow-env backend/channels/gowa-bridge/index.ts
```
